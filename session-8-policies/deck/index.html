MOI Builders · Session 8

Access policies

Friday 4 September · 4pm IST · live on devnet
Start here

You give an agent authority
to act as you. Where does that live?

What the agent does becomes transaction logs. What it acts under — your preferences, your limits, your grant — is you.
MOI gives the participant a computational existence, so none of that leaves with you.
02
How it works today

The app — or the agent — keeps its own copy of you.

On Ethereum a contract owns its storage. Off chain, the same shape: the service owns the row. Either way your preferences and your grants live inside the thing you were using.
Scattered
One copy per service
Ten agents, ten services — you re-teach your preferences ten times. No single you.
Or the agent holds it
The agent becomes the central point
Hand it your preferences and they live inside the agent. Move to a different agent and you start from zero.
Not yours to revoke
Their database, their rules
Taking your authority back means asking them to do it.
03
So MOI moved the data.

Your state lives on your account.

04
Why that is worth doing

One account. Every agent you
ever hire reads and writes there.

One place, and it is yours
Not ten copies of you
Your preferences and your grants sit on one account you control, instead of scattered across ten services that each own their slice.
Agents compose
The next one picks up where the last left off
A new agent reads the same state the last one worked from, because they read the same account. Nobody has to build an integration between them.
Swap without losing anything
Fire the agent, keep yourself
Your state was never the agent's to take. Replace it tomorrow and the new one starts with everything you told the old one.
05
The part nobody asks about

If your data is on your account,
programs must be able to write to accounts they do not own.

On Ethereum the question never comes up. Your account holds a balance and a nonce. It has no storage a contract can write into. Data lives inside the contract.
So MOI is not relaxing a safety rule. It is creating a capability that did not exist.
Open that capability and you immediately owe an answer: who is allowed to, and for what?
06
Why not just write a rule

The agent holds
its own key.

Put the rule in a program and the agent has to choose to call it. Any limit it looks up is one it can decline to look up. You are not constraining it. You are asking it nicely.
07
The answer

One grant, on your account.

The protocol reads it before any foreign write lands. The program asking never touches it.
Which program
The logic allowed to write
Named by its logic id, not a slot and not a person.
What it may do
Mutate your storage
The one action live on the network today.
Who is behind it
The origin of the call
Pin the grant to one agent. Nobody else qualifies.
08
The setup

Two accounts. One experiment.

The owner
Owns the counter
Signs the grant and the revoke. The policy becomes state on this account.
The agent
A separate account, its own key
Signs every write attempt. Holds its own fuel. Is never asked for permission.
Today both keys sit in one demo wallet, for convenience. The chain cannot tell, and does not care — it sees two unrelated accounts. Swap in any agent, any key, any vendor: same rules, same refusal, same grant.
09
The logic

Thirty lines. No permission checks.

coco Ticker state actor: // each participant's counter lives on THEIR account counter U64 endpoint dynamic TickMy() -> (counter U64): mutate c <- Ticker.Sender.counter: c += 1 endpoint dynamic TickAny(participant Identifier) -> (counter U64): mutate c <- Ticker.Actor(participant).counter: // a FOREIGN write c += 1 // abridged — full 30 lines in the repo
No if sender == owner. No owner field. No guard. All of that lives on the account.
10
The attempt

What the agent actually sends.

// scripts/tick.ts — signed by the AGENT's own key const ticker = await getLogicDriver(config.logicId, agent.wallet); const ix = await ticker.routines.TickAny(owner.address).send({ // declares what the call touches — a heads-up, not a permission participants: [{ id: owner.address, lock_type: LockType.MUTATE_LOCK }], fuel_limit: FUEL_LIMIT, // explicit, so the refusal happens ON CHAIN });
A real one, sent with no policy in place: 0x9fc1eff1…c9d4cbe1 — accepted, mined, charged 86 fuel.
11
The grant

One interaction, signed by the owner.

// scripts/grant.ts — signed by the OWNER await new Access(owner.wallet) .storage(config.logicId) // WHICH program may write .allow(AccessAction.STORAGE_MUTATE) // WHAT it may do .caller(access.anyCaller()) .origin(access.callers(agent.address)) // WHO must be behind it .create() .send();
Your authority, as state on your account. The agent is not asked. It cannot decline. It finds out when it tries.
12
Where the check happens

No permission check until the write itself.

The interaction is signed, mined and charged either way. The runtime is the thing that refuses, so there is no version of the agent that skips this step.

What the chain says
// receipt status: 1 — mined, charged, reverted builtin.AccessError: actor is not allowed to write into other actor's storage
Not a script deciding to stop. The runtime refused the write at the instruction, and the interaction is public, on the ledger, and paid for.
15
Revocation

Grant in one interaction.
Revoke in one.

No redeploy. No key rotation. No asking the agent to behave. The next write simply fails.
